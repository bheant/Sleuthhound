# Security

Business data is encrypted in the browser with a key the server never receives. This document describes the key scheme, what the server stores, and the limits of the design.

## Key derivation

All cryptography uses WebCrypto (`lib/account/keys.ts`, `lib/vault/crypto.ts`). The scheme follows the one Bitwarden uses.

```
master   = PBKDF2-SHA256(password, salt = email, 600,000 iterations)
authKey  = HKDF(master, "sleuthhound auth v1")    sent to the server at log-in
vaultKey = HKDF(master, "sleuthhound vault v1")   stays in the browser
dataKey  = 32 random bytes                         encrypts the database
```

The database is encrypted with `dataKey`. That key is wrapped twice: once with `vaultKey` and once with a key derived from the recovery code. The server stores both wrapped copies but can't unwrap either.

A password change re-wraps `dataKey` with the new `vaultKey`. The database itself isn't re-encrypted.

The recovery code is 120 random bits, shown once at sign-up. It has enough entropy that HKDF is used directly, without a slow KDF.

Every encrypted payload uses AES-256-GCM with a random 12-byte IV. The additional authenticated data identifies the payload type (database, backup, password-wrapped key, recovery-wrapped key), so a payload of one type can't be decrypted as another.

The server stores `authKey` as a salted SHA-256 hash. `authKey` is already the output of 600,000 PBKDF2 iterations, and a slow server-side hash wouldn't fit within the 10 ms CPU limit on Cloudflare's free plan.

## Server-side data

The account database schema is in `d1/migrations/`.

| Table | Contents |
| --- | --- |
| `users` | Name, email, business name, role, salted hash of `authKey`, both wrapped data keys, hashed reset token |
| `logins` | Log-in time and the country reported by Cloudflare |
| `sessions` | SHA-256 of each session token and its expiry |
| `invites` | SHA-256 of each invite token, creator and redeemer |
| `rate_limits` | Attempt counters keyed by a hash of the IP address or email |

The server never stores leads, sources, notes, files, API keys, passwords or `vaultKey`. Admins can see `users` and `logins` on the admin page.

## Sessions

Sign-up requires an invite. Invite links are shown once and stored only as a hash.

Sessions use a random 32-byte token in an `HttpOnly; Secure; SameSite=Strict` cookie that expires after 30 days.

Log-in is rate limited to 10 attempts per IP address and 5 per email address in a 15-minute window. Sign-up, password reset and invite redemption have separate limits, defined in `server/rate-limit.ts`.

## Client-side storage

`dataKey` is held in memory only while the vault is unlocked. Locking clears it. The vault locks automatically after 30 minutes of inactivity, which the user can change. Only one tab can hold the vault at a time.

The database is saved to IndexedDB as a single encrypted snapshot. Backups are exported as a `.sleuthhound` file encrypted with `dataKey`.

The Content-Security-Policy is generated by `scripts/headers.mjs`. It allows scripts from the site and the specific inline scripts Next.js emits (by hash), and network connections only to the site and the listed providers.

## Proxy

Apollo and HubSpot don't support CORS, so requests to them go through `functions/proxy/`. The function:

- rejects requests without a valid session or from another origin
- forwards only the `accept`, `authorization`, `cache-control`, `content-type` and `x-api-key` headers, and never the session cookie
- doesn't store or log anything
- sets `Cache-Control: no-store` on responses

The user's Apollo or HubSpot key is sent in the request headers, so it's present in the function's memory while the request is handled. It's sent over TLS and never written to storage.

## Limitations

- Served code: the browser runs whatever JavaScript the server sends. If the site or the Cloudflare account were compromised, modified code could capture the password. This applies to any encrypted web app. Self-hosting from this repository removes that dependency.
- LLM providers: reviews send the target's details, the ideal-client description and recent decisions to the selected provider, under the user's API key and that provider's terms.
- Local access: anyone with access to an unlocked tab, or a malicious browser extension, can read the data.
- Lost credentials: if a user loses both their password and recovery code, the data can't be recovered. An admin password reset only restores access if the user still has the recovery code. Backups are the other fallback.
- Hosting: Cloudflare hosts the site and the account database, and can see request metadata such as IP addresses.
